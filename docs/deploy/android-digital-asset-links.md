# Android Digital Asset Links

AvenOS publishes its Android association at:

```text
https://aven.id/.well-known/assetlinks.json
```

The association authorizes package `ceo.aven.os` for Android App Links and
Credential Manager passkeys. It is generated by `aven-identity` from the configured
signing-certificate allowlist; there is no manually edited JSON file on the
deployment host.

## Published contract

The endpoint returns HTTP 200 without a redirect and an `application/json`
content type. Its payload has this shape:

```json
[
  {
    "relation": [
      "delegate_permission/common.handle_all_urls",
      "delegate_permission/common.get_login_creds"
    ],
    "target": {
      "namespace": "android_app",
      "package_name": "ceo.aven.os",
      "sha256_cert_fingerprints": ["AA:BB:...:FF"]
    }
  }
]
```

Only SHA-256 certificate fingerprints belong in the array. Do not use a file
checksum, a SHA-1 fingerprint, or the keystore password. The API normalizes
valid fingerprints to uppercase. It returns 503 when the allowlist is absent.
A signed Android release must treat that response as a failed identity
deployment and stop before distributing the application.

## GitHub Actions configuration

Configure these secrets in the protected `next` GitHub Environment:

- `ANDROID_KEYSTORE_BASE64`: the complete upload keystore, base64 encoded on one
  line;
- `ANDROID_KEYSTORE_PASSWORD`: the keystore password;
- `ANDROID_KEY_ALIAS`: the upload-key alias;
- `ANDROID_KEY_PASSWORD`: the private-key password.

CI derives the direct-release fingerprint from `ANDROID_KEYSTORE_BASE64`; do not
copy it into another variable. If Google Play App Signing is enabled, configure
its certificate separately as the optional `next` Environment variable
`ANDROID_PLAY_APP_CERT_SHA256_FINGERPRINTS`. It may contain comma-separated
fingerprints during a Play signing-key rotation.

The upload and Play certificates are normally different. Set the
repository-level variable `ANDROID_RELEASE_ENABLED=true` only after all four
signing secrets are present.
Repository scope is required because the Android job's `if` expression is
evaluated before the job enters the `next` Environment.

### Initial setup

The keystore path is not created by the Android build. Generate it first, or use
an existing organization-owned Android upload keystore. The following commands
create a new key at a concrete path outside the repository:

```sh
export ANDROID_KEYSTORE="$HOME/.config/avenos/android-release/upload-keystore.jks"
install -d -m 700 "$HOME/.config/avenos/android-release"

keytool -genkeypair \
  -keystore "$ANDROID_KEYSTORE" \
  -storetype PKCS12 \
  -alias avenos-upload \
  -keyalg RSA \
  -keysize 4096 \
  -sigalg SHA256withRSA \
  -validity 10000 \
  -dname 'CN=AvenOS Upload, O=MyAvenCEO, C=DE'

chmod 600 "$ANDROID_KEYSTORE"
```

`keytool` asks for a strong keystore password. PKCS12 uses that password for the
private key as well, so enter the same value later for both CI password secrets.
If the command reports that the file does not exist during `-exportcert`, the
generation command above did not complete or `ANDROID_KEYSTORE` points somewhere
else.

Keep the recovery copy outside Git and GitHub. Back it up in the organization's
encrypted credential store before enabling CI; an Actions secret cannot be read
back later. Losing the keystore may prevent updates to directly distributed APKs.

Inspect the upload certificate:

```sh
keytool -exportcert \
  -keystore "$ANDROID_KEYSTORE" \
  -alias avenos-upload \
  -rfc |
  openssl x509 -noout -fingerprint -sha256
```

After reviewing the printed fingerprint, configure Actions from an authenticated
GitHub CLI session:

```sh
openssl base64 -A -in "$ANDROID_KEYSTORE" |
  gh secret set ANDROID_KEYSTORE_BASE64 --env next
gh secret set ANDROID_KEYSTORE_PASSWORD --env next
printf '%s' avenos-upload | gh secret set ANDROID_KEY_ALIAS --env next
gh secret set ANDROID_KEY_PASSWORD --env next

gh variable set ANDROID_RELEASE_ENABLED --body true
```

The password commands intentionally omit `--body`; `gh` prompts for each value.
Enter the password used by `keytool` for both. The keystore pipeline sends its
encoded bytes through standard input rather than a command-line argument.

If Google Play manages the app signing key, download the SHA-256 certificate
fingerprint from Play Console's **App integrity** page and configure it without
repeating the upload certificate:

```sh
gh variable set ANDROID_PLAY_APP_CERT_SHA256_FINGERPRINTS \
  --env next \
  --body '11:22:...:00'
```

## Deployment behavior

The association document belongs to the identity release, not the checkout or
facade. Before distributing a signed Android build:

1. extract the upload certificate from the protected release keystore and merge
   any configured Play App Signing certificates;
2. render the exact fingerprint allowlist into the mode-0600 identity runtime
   environment;
3. deploy `aven-identity`, whose well-known route renders the JSON;
4. fetch the public HTTPS URL and require HTTP 200 plus JSON content type;
5. verify the exact expected fingerprint set, package name, App Links relation,
   and login-credentials relation; and
6. check the release certificate again before signing the APK.

The current service deployment is described in the authoritative
[deployment handbook](../operations/deployment.md).
Android release automation must retain these checks when it is added to the
new platform workflows.

## Verification

After the `deploy identity stack` job succeeds:

```sh
curl --fail --silent --show-error \
  --dump-header /tmp/assetlinks.headers \
  https://aven.id/.well-known/assetlinks.json |
  jq .

tr -d '\r' < /tmp/assetlinks.headers |
  grep -i '^content-type: application/json'
```

Also test the installed, release-signed APK on a physical Android device. A
debug APK uses a different certificate and is deliberately not associated with
the hosted identity origin.

## Certificate rotation

Never replace a fingerprint in one step while installed builds still use it.

1. Append the new Play certificate fingerprint to
   `ANDROID_PLAY_APP_CERT_SHA256_FINGERPRINTS`, or update the complete CI
   keystore secret set for a direct-distribution certificate rotation.
2. Deploy and verify that both old and new fingerprints are published.
3. Release builds signed by the new certificate.
4. Keep the old certificate published until all supported installations have
   migrated or expired.
5. Remove the old fingerprint and deploy again.

For a Play signing-key upgrade, follow Play's overlap window and publish every
certificate Play may use during the transition. Upload-key rotation is separate:
update all four CI signing secrets together, retain a backed-up copy, and leave
the Play App Signing fingerprint in the allowlist.
